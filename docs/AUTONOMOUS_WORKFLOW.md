# 자율 제작·검증 실행

그래프 라이브러리의 **↻ 자율 제작 그래프**로 새 프리셋을 만든 뒤 CLI·모델·목표·대상 프로젝트를 지정한다. 이 프리셋은 계획 1개를 자동 선택하고, 구현 → 테스트 → 읽기 전용 검토 → 최종 승인으로 진행한다. 기존 그래프의 계획 승인 설정은 변경하지 않는다. CLI에서는 `agent-loop init --autonomous`로 같은 프리셋을 추가할 수 있다.

그래프 설정의 `자동 수정 루프`는 실패를 구현으로 되돌리며 기본 3회까지 수정한다. `실제 브라우저 검증 필수`가 켜진 웹 작업은 실제 플랫폼 검증 명령의 네이티브 종료 코드 0이 추가로 필요하다. 웹이 아닌 작업은 이 옵션을 끄고 해당 프로젝트의 실제 테스트를 사용한다. 빈 검사·보고서만 작성한 실행·생략·실패·낡은 근거로 SUCCESS를 만들지 않는다.

## 준비와 권한

- Node 24 이상과 인증된 로컬 코딩 CLI, 대상 프로젝트의 테스트 실행 환경이 필요하다.
- 웹 작업에는 `playwright`와 Chromium이 대상 프로젝트 또는 Agent Graph 설치 환경에 있어야 한다. 없으면 구현 역할이 기존 승인된 CLI 도구로 프로젝트 내부 설치를 준비할 수 있다. 설치·네트워크·권한이 거부되면 대기한다. npm 배포에 브라우저를 묶거나 자동으로 전역 설치하지 않는다.
- Codex의 `네이티브 자동 승인 검토`는 `--approve-for-me`를 지원하는 CLI에서만 사용한다. 쓰기 역할의 개별 명령을 네이티브 검토자가 승인하며 workspace-write를 사용한다. `--sandbox`와 충돌하는 인자를 함께 전달하지 않는다. 읽기 전용 역할에는 적용하지 않는다. 사용자 전역 CLI 설정은 바꾸지 않는다.
- Kilo 등 다른 CLI는 기존 네이티브 명령 승인 정책을 사용한다. 무인 실행 전에 필요한 프로젝트 명령이 해당 정책에서 허용돼 있어야 한다. 그래프는 인증·권한 거부·명시적 사람 승인을 자동 우회하지 않는다.

## 브라우저 검사 명세

구현/테스트 역할이 `.agent-graph/browser.json`을 작성한다. 검사 조건은 원래 요구사항을 충족해야 하며, 실패를 없애기 위해 명세·테스트를 약화하면 안 된다. 계획·검토·최종 승인 역할은 이 명세와 실제 테스트 기록을 읽기 전용으로 검토한다. 원래 사용자가 사람의 승인이나 운영자 전용 증거를 명시했다면 그 조건은 계속 지킨다. 자율 작업의 새 목표에는 불필요한 운영자 전용 보고서 조건을 추가하지 않는다.

```json
{
  "version": 1,
  "server": { "command": ["node", "server.mjs"] },
  "steps": [
    { "id": "desktop", "type": "viewport", "width": 1280, "height": 900 },
    { "id": "page", "type": "visible", "selector": "h1" },
    { "id": "move", "type": "click", "selector": "#move" },
    { "id": "score", "type": "text", "selector": "#score", "equals": "1" },
    { "id": "save", "type": "snapshot", "name": "score", "selector": "#score" },
    { "id": "reload", "type": "reload" },
    { "id": "persist", "type": "sameSnapshot", "name": "score", "selector": "#score" },
    { "id": "mobile", "type": "viewport", "width": 390, "height": 844 },
    { "id": "bounds", "type": "noOverflow" },
    { "id": "cells-fit", "type": "within", "selector": ".cell", "container": "#board" },
    { "id": "console", "type": "noConsoleErrors" }
  ]
}
```

지원 단계는 `viewport`, `click`, `press(key)`, `drag(selector,direction)`, `reload`, `visible`, `text(equals/contains)`, `count(equals)`, `noOverflow`, `within(selector,container)`, `snapshot(name,selector)`, `sameSnapshot`, `differentSnapshot`, `noConsoleErrors`, `http(path,status,contains)`이다. 모든 단계의 id는 고유해야 하고, 실제 assertion이 최소 하나 있어야 한다. 한 실행은 최대 100단계·120초, 파일 해시는 최대 10,000개를 허용한다. assertion은 최대 5초간 상태가 안정되는지 재확인한다. 소스 심볼릭 링크는 명시적인 프로젝트 복사본으로 풀어야 하며 제한을 넘으면 성공 대신 실패/대기로 끝난다. `http`는 경로를 미리 정규화하지 않는 실제 loopback HTTP 요청이므로 encoded traversal·잘못된 URL도 직접 검사할 수 있다. DOM mock은 브라우저 검증으로 인정하지 않는다.

서버 명령은 argv 배열이며 셸 래퍼 없이 대상 프로젝트에서 시작한다. 제공된 전용 임시 `PORT`를 사용하고 실제 `http://127.0.0.1:포트`를 출력해야 한다. 다른 포트를 출력하면 기존 서버를 재사용하지 않고 실패한다. 빌드가 필요한 프로젝트는 먼저 빌드해야 한다. 검사 중·서버 종료 중 소스가 바뀌면 다시 검사해야 한다. 브라우저 요청은 이 loopback origin으로 한정한다.

일반 수동 실행은 `agent-loop verify-browser --spec .agent-graph/browser.json`으로 가능하다. 자율 그래프는 프롬프트에 제공된 **설치된 플랫폼 CLI의 정확한 절대 경로 명령**을 실행해야 한다. 프로젝트가 만든 가짜 CLI나 `--help` 실행은 네이티브 브라우저 증거로 수락하지 않는다. 단위 검사를 먼저 실행한 뒤 브라우저 명령을 마지막에 실행한다. 네이티브 명령의 명시적인 `cd`가 이미 승인된 동일 대상 디렉터리를 가리키면 같은 검사로 정규화한다; 다른 디렉터리·추가 인자·파이프·실패 마스킹은 동일 검사로 수락하지 않는다. 디렉터리 생성·로그 읽기·보고 출력은 별도 호출로 하고, 검사 뒤에 echo·파이프·백그라운드 실행을 붙이지 않는다.

`verification/browser/<run-id>/`에 성공/실패별 report.json, 서버 로그, 최종/실패 화면, viewport 화면과 trace.zip을 보존한다. `verification/browser/report.json`은 최근 실행의 원자적 복사본이다. 보고서는 검증기가 직접 쓰며 모델이 작성하지 않는다. 새 검사를 실행해도 과거 실패 폴더를 덮어쓰지 않는다. 실행한 서버와 브라우저만 정리하며, 외부 서버는 종료하지 않는다. 실패·취소·정리 불확실·미실행 단계는 성공으로 승격하지 않는다.

## 실패·재시도

- 테스트 assertion 실패는 FAIL, 검토/승인 반려는 REJECTED로 구현에 돌아간다.
- 모델이 BLOCKED로 보고한 수정 가능한 코드/검사 준비 문제는 `BLOCKED_KIND: product` 또는 `BLOCKED_KIND: test_setup`과 실제 근거를 포함한다. 자율 그래프에서만 실패 경로로 돌린다. 기존 수동 그래프의 BLOCKED 동작은 유지한다.
- 실제 네이티브 권한 오류는 위 표식보다 우선하여 대기한다. 외부 서비스·인증·명시적인 사람 증거는 `BLOCKED_KIND: external`로 보고한다.
- 테스트 역할의 제품 파일 변경은 네이티브 변경 경로와 실행 전후 파일 해시로 감지해 반려한다. 테스트·검증 명세·로그는 별도 경로에서 작성하고, 제품 수정은 구현에서 수행한다. 빌드 산출물과 테스트 결과는 제품 수정 검사에서 제외하되 실제 브라우저 검증의 소스·자산 해시에는 빌드 산출물을 포함한다.
- 사용자 Interrupt/STOP, 수동 계획 승인, 추가 접근 승인, 무료/유료·미확인 모델의 기존 복구 한도는 유지한다. 무료도 무한 반복하지 않고 유료·가격 미확인은 공급자 한도에 도달하면 추가 호출을 멈춘다.
- 기존 블록 보고의 형식 보완은 현재 네이티브 실행 기록을 기준으로 한다. 기록이 없으면 새 검사를 실행하고, 실패 기록을 PASS로 바꾸지 않으며, 유효한 성공 기록이 있으면 파일 수정 없이 정확한 CHECK_COMMAND로 보고만 보완한다.

검증기는 실제 실행 여부와 관측된 assertion을 증명한다. 원래 목표에 충분한 검사인지, 모델이 구현을 올바르게 수정했는지는 별도의 테스트·검토·최종 승인 책임이다. 프리셋은 사람 검토를 가장하거나 공급자 가용성을 보장하지 않는다.

## 공급자·계획 형식 복구

네이티브 연결 로그와 `step_start`/`step_finish`, 빈 텍스트, 실패한 도구 이벤트는 유효한 모델 진행으로 대기 시간을 연장하지 않는다. 동일한 주 요청의 공급자 오류가 유효한 진행 없이 3회 반복되면 현재 프로세스를 종료하고 기존 유한 재시도·무료 모델 복구 정책에 넘긴다. 중복된 동일 로그는 횟수에 포함하지 않는다. 보조 제목 생성 세션의 오류는 원시 로그에 남기되 주 요청의 진단·재시도 원인으로 사용하지 않는다. 상태코드 없이 기록된 네이티브 Service Unavailable·Bad Gateway·Gateway Timeout·Internal Server Error도 같은 유한 연결 복구에 포함한다. 실제 401/403 인증·권한 중단 정책은 유지한다.

동일한 도구 스키마/사용 불가능 오류가 서로 다른 호출에서 3회 연속 관측되면 `tool_arguments`로 중단한다. `write`의 잘못된 인수는 2회에서 다음 유한 시도로 전환한다. 정상 도구 완료나 다른 오류는 이 연속 횟수를 초기화한다. 같은 연결에서 write 스키마 실패가 관측된 뒤 Kilo의 후속 쓰기 역할은 호출별 유효 에이전트 설정으로 `write`와 그 공유 edit 그룹을 제외하고, 허용된 bash의 작은 인용 heredoc으로 파일을 작성·수정한다. 빈 호출의 내용을 추측하거나 전역 CLI 설정·모델·bash 승인 정책·전체 예산을 변경하지 않는다. 읽기 전용 역할에는 이 쓰기 대체 경로를 추가하지 않는다.

이 대체 경로는 12초로 제한한 `kilo debug config` 조회에서 에이전트 이름만 추출해 실행 전 설정에 적용한다. 모델 호출은 없으며 원시 설정·인증 정보는 로그나 새 설정에 복사하지 않는다. 조회가 실패하면 오류 출력 내용을 노출하지 않고 실행을 중단한다. 설정 조회 시간도 전체 실행 시간 예산에 포함된다.

## Kilo 검사 명령과 구현 완료 형식

고정 계약을 사용하는 Kilo 쓰기 역할에는 호출별 네이티브 플러그인을 연결한다. 등록된 검사와 정확히 같은 기본 명령 뒤의 `head`/`tail`/인용 grep 표시 파이프나 `; echo "exit: $?"`만 등록 원문으로 교체한다. **교체 후의 명령이 기존 Kilo bash 권한 검토와 실제 실행을 거친다.** 런타임이 별도 셸로 승인을 우회하지 않는다. 알 수 없는 명령·다른 cwd·추가 인수는 교체하지 않으며, 등록 검사 뒤의 그 외 명령 연결은 거부한다. 파이프·마스킹 자체를 성공 receipt로 인정하는 규칙은 추가하지 않는다. 기존 CLI 플러그인과 권한 설정, 수동 그래프와 다른 공급자는 유지한다.

자율 구현 역할에서만 마침표 등으로 끝나는 평문 마지막 문장에 붙은 단일 `[PHASE_DONE]`을 독립 행으로 정규화한다. 원시 assistant 응답은 로그에 보존한다. 인용·코드 fence·중복·뒤에 텍스트가 있는 표식이나 누락 표식은 보완이 필요하다. 이 처리는 구현 단계의 종료만 나타내며, 테스트·검토·최종 승인 및 SUCCESS 조건을 충족시키지 않는다. 수동 그래프와 감사 역할의 완료 형식 검사는 그대로 유지한다.

네이티브 훅 인터페이스는 [Kilo 공식 플러그인 문서](https://kilo.ai/docs/automate/extending/plugins)의 `tool.execute.before`를 사용한다. npm 패키지에도 이 로컬 플러그인과 필요한 모듈을 포함한다.

계획 선택지마다 모든 고정 요구사항을 참조해야 하며 프롬프트는 전체 ID 표기를 권장한다. 계획의 명확한 `REQ-006/007`, `REQ-006,007`, `REQ-001..024` 목록·범위는 알려진 ID 집합으로 해석하되 원래 계획 본문을 고치지 않는다. 알려지지 않은 끝점·역방향 범위·실제 누락은 선택지별로 알리고 보고를 보완한다. 이 정규화는 계획 참조에만 적용하며 테스트·QA·최종 승인의 각 고정 ID 증거 블록과 실제 실행 게이트에는 적용하지 않는다.

일부 네이티브 검사만 성공한 경우에는 전체 검증이 완료된 것으로 간주하지 않는다. 이전 보고의 CHECK_COMMAND와 수락된 성공 기록을 대조해 빠진 실제 검사만 단독 명령으로 실행하도록 보완한다. 모든 보고된 검사 기록이 이미 있을 때만 형식 보완으로 처리한다. 계획·QA·최종 승인 역할에는 브라우저 명령을 계획/감사 대상으로만 제공하며 실행이나 명세 작성을 지시하지 않는다. 검증기가 설치 위치의 Playwright를 사용할 수 있으므로 대상 프로젝트의 require 실패만으로 환경 제약을 선언하지 않는다.

## 고정 검증 계약과 구조화 보고

새 자율 프리셋은 `automation.verificationContract=true`를 사용한다. 기존 그래프 version 2·연결 version 1·세션 stateVersion 3과 localStorage 키는 유지한다. 이 옵션이 없는 기존 그래프는 종전 보고 계약을 사용한다.

대상 프로젝트의 `.agent-graph/verification.json`은 필수 검사와 요구사항 연결을 선언한다. 시작 전에 제공된 계약은 첫 모델 호출 전에 보호 파일과 함께 SHA-256으로 고정하며 출처는 `supplied`로 기록한다. 없으면 구현 역할이 인수 테스트와 계약을 만들고 첫 테스트 진입 때 고정한다(`implementation`). 계약 누락·오류는 테스트 준비 실패로 구현에 돌아가며 유한 수정 한도 안에서 처리한다. 시작 전에 잘못된 계약이 있으면 호출 없이 요청을 거부한다.

```json
{
  "version": 1,
  "protectedFiles": ["tests/verify-acceptance.mjs", ".agent-graph/browser.json"],
  "checks": [
    { "id": "acceptance", "command": "node tests/verify-acceptance.mjs", "requirements": ["REQ-001"] },
    { "id": "browser", "command": "<프롬프트가 제공하는 설치된 플랫폼의 정확한 명령>", "requirements": ["REQ-001"] }
  ]
}
```

모든 고정 REQ ID가 검사에 연결돼야 하며 **등록된 모든 검사**가 테스트 역할에서 실제 성공해야 한다. 한 검사가 모든 ID에 연결돼 있어도 다른 검사를 생략할 수 없다. 등록된 npm 검사 script와 npm run 참조에서 관측 가능한 || fallback·파이프·백그라운드·exit 0·선택 실행 플래그는 테스트 전에 준비 실패로 구현에 돌린다; 임의의 외부 runner 내부 의미까지 증명하는 정적 분석은 아니다. 웹 계약은 플랫폼 브라우저 명령과 보호된 browser.json을 포함한다. npm script 이름만 등록하는 대신 보호된 인수 검사 실행 파일을 직접 실행하는 검사도 필요하다. 보호 파일은 최대 200개·개별 10MiB·전체 50MiB이며 심볼릭 링크와 프로젝트 밖 경로는 거부한다. 계약 자체도 보호한다. 매 시도 전후와 성공 종단에서 해시를 확인하며, 보호 파일 변경·삭제·읽기 실패 또는 네이티브 이벤트의 쓰기 관측(원상복구 포함)은 BLOCKED가 된다. 이 검사는 적대적인 운영체제나 악성 CLI를 격리하는 보안 샌드박스는 아니다.

고정 계약의 테스트·검토·최종 승인 역할은 아래 형식으로 판단만 보고한다. CHECK_COMMAND나 PHASE_DONE을 모델이 복사할 필요가 없다.

```text
[AGENT_REPORT]
{"version":1,"verdict":"PASS","requirements":[{"id":"REQ-001","status":"SATISFIED","evidence":"관측한 assertion과 결과"}]}
[/AGENT_REPORT]
```

테스트 verdict는 PASS/FAIL/BLOCKED, 검토·승인은 APPROVED/REJECTED/BLOCKED이다. 요구사항 status는 SATISFIED/PARTIAL/FAILED/BLOCKED이며, PASS/APPROVED에는 모든 고정 ID가 필요하다. 오류 보고에는 실패한 항목만 넣어도 된다. BLOCKED에는 `blockedKind: product|test_setup|external`을 사용할 수 있다. 엔진이 고정 검사 ID와 실제 네이티브 명령·종료코드·receipt ID를 연결해 기존 화면용 증거로 변환한다. 형식 오류·중복·알 수 없는 ID를 거부하고, 실제 검사 실패·미실행·권한 오류를 성공으로 바꾸지 않는다. 검토와 최종 승인은 현재 테스트 증거를 읽기 전용으로 감사한다.

검사 연결과 고정 해시는 검사의 실행·보존을 증명한다. 검사 내용이 도메인의 모든 요구사항을 충분히 검증하는지는 인수 테스트 작성자와 독립 검토의 책임이다. 모델이 직접 만든 검사의 출처를 외부에서 제공된 인수 기준과 동일하게 표현하지 않는다.

## 자체 Node 테스트의 영역별 계약과 독립 검토

새 자율 프리셋은 `automation.authoredNodeTests=true`를 사용한다. 고정 계약에 `npm test`가 있으면 `nodeTests` 정책도 필수다. 기존 그래프에 이 선택 필드가 없으면 종전 동작을 유지한다. UI의 **자체 Node 테스트 계약 필수** 설정으로 제어하며 다른 데이터 버전이나 저장 키는 변경하지 않는다.

`nodeTests`는 `suiteCheckId`(실제 `npm test` 검사), `checkId`(플랫폼이 제공하는 정확한 `verify-node-tests` 명령), `scopes`를 선언한다. 각 영역은 고유한 `id`, 직접 작성할 `test/*.test.mjs` 파일, 요구사항 ID, 정확한 `cases` 이름, 보호된 `challenges` 목록을 가진다. 예를 들어 2048은 엔진·컨트롤러·저장·HTTP를 각각 선언한다. 컨트롤러의 실제 이동/스폰/점수, 저장 어댑터의 직렬화/복구/예외, 포트 0의 실제 HTTP 요청과 서버 종료를 자체 assertion으로 검사한다. 제공된 인수 검사만 호출하는 파일은 자체 테스트로 인정하지 않는다.

각 challenge는 `{id,adapter,targets}`로 선언한다. 보호된 ESM adapter는 `mutate({root,enabled,id})`에서 선언된 제품 파일의 대체 소스 문자열 맵을 반환한다. `enabled=false`는 같은 래퍼의 무결함 대조군이고 `true`는 지정 결함이다. 테스트·package.json·보호 파일은 교체할 수 없다. 구현자는 테스트에서 adapter나 결함 ID를 검사하지 않고 공개 동작을 assertion으로 확인한다.

`npm test`는 `node --test --test-concurrency=1 <영역 파일들을 선언 순서대로>`와 정확히 일치해야 한다. 별도의 `agent-loop verify-node-tests`는 원본을 바꾸지 않고 격리 복사본에서 영역별 baseline, 각 무결함 대조군, 제품 결함을 순서대로 실행한다. 제공된 인수 검사/계약은 복사본에서 제외한다. 필수 이름은 정확히 한 번 성공해야 하고 skip/todo/cancel은 실패다. 결함 검사는 해당 영역의 필수 case에서 **실제 `ERR_ASSERTION`**이 발생해야 통과한다. 문법·import 오류, 단순 출력, timeout은 결함 탐지로 인정하지 않는다. Node의 `node:test.run` 구조화 이벤트를 사용한다([Node 24 테스트 API](https://r2.nodejs.org/docs/latest-v24.x/api/test.html)).

결과는 `verification/node-tests/<run-id>/`와 `verification/node-tests/report.json`에 남긴다. 소스·자체 테스트 해시, 영역별 case, 대조군, 탐지 assertion, 소유 프로세스 종료와 임시 복사본 정리 결과를 기록한다. 작업당 20초·전체 180초 상한이 있으며 실패도 보고서를 남긴다. 성공 보고도 현재 소스 해시와 재대조하며 native suite·품질 검사 양쪽의 실제 종료 코드 0이 있어야 테스트 PASS를 수락한다.

CLI stdout에는 영역별 대조군·결함 결과와 오류를 축약해 출력하고 전체 보고서는 파일에 보존한다. timeout·취소 사유와 실패 경로의 정리 조건을 앞부분에 표시해 도구의 출력 절단 때문에 복구 근거가 가려지지 않게 한다. HTTP 테스트는 assertion 전에 `t.after` 또는 `try/finally`를 등록해야 하며, assertion 뒤의 종료 코드만으로는 실패 경로 정리가 보장되지 않는다.

정책이 있는 테스트·검토·최종 승인 보고에는 아래와 같이 **모든 영역**의 판단이 추가로 필요하다.

```json
{"testScopes":[{"id":"controller","status":"SATISFIED","evidence":"실제 테스트 파일, assertion, 대조군과 탐지한 결함 근거"}]}
```

읽기 전용 검토자와 최종 승인자는 각 자체 테스트 파일과 `verification/node-tests/report.json`을 네이티브 `read`/`Read` 또는 단독 `cat`/`Get-Content`로 읽어야 한다. 완료된 실제 읽기 기록을 별도 보존하며 주장 문장·실패한 읽기·검사 재실행은 대신할 수 없다. 두 역할의 영역별 판단, 현재 테스트 역할의 품질 보고 digest, 실제 검사 이력이 모두 일치해야 SUCCESS로 이동한다. 이는 선언한 경계의 검증 강도이며 모든 가능한 결함이나 적대적인 테스트 코드를 격리·증명하는 보안 장치는 아니다.

## 전체 실행 예산

새 실행에는 단계 복구 예산과 별개로 `sessionTimeoutMs`(기본 60분), `maxSessionAttempts`(기본 24회)를 저장한다. 화면의 전체 시간·전체 에이전트 시도 한도에서도 설정한다. 시간은 시작부터 대기·백오프·재개·재시작 시간을 포함한 wall-clock이다. 시도 수는 네이티브 에이전트 CLI 호출 수이며 보고 보완·무료 복구도 포함한다. **CLI 내부의 공급자 요청 수·토큰·금액을 제한하는 과금 예산은 아니다.**

한도가 소진되면 PAUSED로 정지하고 자동 복구 예약을 취소한다. 실행 중에는 전체 마감 시각으로 자식 CLI를 종료한다. 예산 소진 상태는 수동 재개·무료 복구·워커 재시작으로 초기화하지 않는다. 마지막 허용 시도가 마감 전에 성공하면 결과를 수락할 수 있다. 기존 저장 세션에 전체 예산이 없으면 종전 정책으로 읽으며 데이터를 자동 변경하지 않는다. 기존에 완료한 SUCCESS 기록은 이후 시간이 지났다는 이유로 무효화하지 않는다.

새 자율 프리셋은 단계 10분·도구 5분·단계 복구 31분·네이티브 기본 시도 3회·각 방문당 무료 추가 복구 1회(15초 대기)를 사용한다. 명시적인 설정값은 우선한다. 공급자 장애·인증·권한·불명확한 워커 소유권은 계속 성공을 차단하며, 예산은 이런 외부 조건의 가용성을 보장하지 않는다.

## 자율 계획의 경로 검토

브라우저 selector의 `text /keep playing/i` 같은 정규식은 파일 접근 요청으로 오인하지 않는다. 자율 계획이 원래 목표·그래프 지시에 없던 외부 경로를 추가하면 실행이나 승인 요청 전에 계획 역할에서 유한 보완한다. 계속 같은 경로를 요구하면 PAUSED로 끝나며 접근을 자동 허용하지 않는다. 원래 사용자가 명시한 외부 경로는 기존 접근 승인 절차를 유지한다. 이 검토는 네이티브 명령별 권한 정책을 대체하거나 변경하지 않는다.

`Handle / -> index.html` 같은 웹 루트 문서 매핑도 HTTP 경로 설명으로 구별한다. 해당 매핑의 `/` 토큰에만 적용하며 같은 줄의 다른 파일 경로나 `FILE_ACCESS: /`는 접근 요청으로 남는다. 파일시스템 루트 조회를 허용하거나 VM·native 도구의 대상 경계를 변경하지 않는다.

## 소스 고정 테스트와 후속 단계 예산

새 프리셋은 `automation.testSourceGuard=true`, `reserveFinalizationBudget=true`를 사용한다. 선택 필드 없는 기존 그래프는 종전 동작을 유지한다. 테스트 역할은 제품·자체 테스트·package/config를 수정하지 않으며, 모든 작성/수정은 구현 역할이 담당한다. Kilo의 호출별 native pre-hook은 쓰기/편집과 등록되지 않은 실행을 차단한다. 등록 foreground 검사, 읽기, verification 디렉터리 준비는 허용하며 기존 native 권한을 확대하지 않는다. 다른 CLI와 숨은 파일 쓰기는 250ms 간격의 소스 해시 검사 및 종료 후 재검사로 보완한다. 이는 보안 샌드박스가 아니다.

테스트 역할의 첫 등록 검사 실패(exit nonzero)는 CLI 트리를 종료하고 실제 진단을 보존한 FAIL로 구현에 반환한다. 환경 권한/인증/사용 불가 모델과 종료 불명 프로세스는 기존 대기·차단 정책을 유지한다. 위반 attempt는 `verificationInvalidation`에 시각·원인·파일을 기록하며 이전 명령/proof를 수락 근거에서 제외한다. 원시 attempt 명령은 이력으로 보존한다. verification 등 출력 디렉터리 준비는 소스 변경과 구분하므로 정상 검사 기록을 지우지 않는다.

PASS 테스트의 전체 소스 snapshot을 저장하고 검토·최종 승인 전후에 다시 대조한다. 변경된 경우 REJECTED로 구현과 전체 검사로 돌아간다. 이전 통과 보고를 수정하거나 부분 검사만 재사용해 승인하지 않는다. 자체 품질 검증은 안전하게 종료된 범위 안에서 여러 영역·결함 실패를 한 실행에 모아 보고한다. 취소나 소유 프로세스 종료 불명은 즉시 중단한다.

전체 60분/24회는 그대로다. 새 프리셋은 방문의 최초 시작 시각을 기준으로 고정 단계 마감을 저장하며 재시도·무료 복구로 갱신하지 않는다. 구현은 최대 전체 시간의 60%를 쓰되 전체 마감 전 30%(기본 18분)를 검증·검토·승인에 남긴다. 테스트는 최종 10%(6분), 검토는 최종 5%(3분)를 남긴다. 계획·테스트·검토의 방문별 상한은 각각 전체의 15%·25%·10%다. 단계별로 후속 호출도 보존하며(구현 기본 4회), 작은 사용자 지정 호출 한도에서는 비례 축소한다. 단계 마감에 미완료면 남은 단계를 건너뛰지 않고 PAUSED로 보존한다. 자동 제품 수정은 새 프리셋 기본 5회이고 전체 시간·호출 한도가 항상 우선한다.

새 프리셋의 `guardOwnedProcesses=true`는 Kilo의 구현·테스트 역할에서 native bash 실행 전 pkill/killall, 프로세스 이름 기반 taskkill/Stop-Process, pgrep 결과에 대한 kill 같은 일괄 종료를 차단한다. 구현에서는 기존 native 권한을 늘리지 않고 유한 tool-argument 복구로 소유 핸들/기록된 PID 정리를 안내하며, 테스트에서는 FAIL로 구현에 반환한다. 일반 프로그램의 내부 동작까지 격리하는 OS 보안 샌드박스는 아니다. 고정 Node 자체 suite와 정확히 같은 직접 `node --test` 호출은 등록된 npm 검사로 정규화해 파이프의 0 종료가 실제 실패를 가리지 않도록 한다.

테스트의 준비·조회 구문은 제품 수리와 구분한다. 같은 프로젝트의 verification 출력 폴더는 상대·인용/공백 이스케이프 절대 경로와 `mkdir -p … && 등록 검사`를 허용한다. 준비 명령이 성공해야 검사가 실행되고 native 전체 종료코드를 그대로 보존한다. 출력 캡처는 등록 검사 경로로 정규화하며 제품 파일 캡처는 차단한다. 제한된 읽기 명령의 `;`/`&&` 연결, literal echo 구분자, Node/npm 버전 조회, stderr 폐기/합치기도 조회로 허용하되 검증 receipt로 인정하지 않는다. 임의 코드 실행·제품 쓰기·다른 프로젝트 이동·파이프의 실패 마스킹·검사 합치기는 계속 거절한다. 비밀값 마스킹은 다음 청크에서 비밀값으로 완성될 수 있는 실제 접미사만 보류해 짧은 정책 오류 이벤트를 watchdog까지 지연시키지 않는다.

## Kilo의 대상 조회 경계

새 자율 프리셋은 `targetScopeGuard=true`다. Kilo의 계획·구현·테스트·검토·최종 승인에 모두 invocation-local hook을 로드한다. native `read/glob/grep` 등의 명시적 파일 경로와 literal shell 조회는 대상 프로젝트 및 사용자가 명시적으로 승인한 추가 경로로 제한한다. 부모 경로·홈 경로·경로 접두사가 비슷한 형제 폴더·외부 심볼릭 링크를 거절하며, 재귀 조회는 외부 링크를 포함하면 실행 전에 차단한다. 경계를 확인할 수 없거나 10,000개 항목 제한을 넘는 재귀 요청은 더 좁은 대상 경로를 사용해야 한다. 기본 native external_directory 정책도 deny로 두며, 기존 read 금지·사용자 plugin과 읽기 전용 역할의 bash/edit 금지는 유지한다. 공급자 CLI 자체의 인증·설정 로딩을 수집하거나 변경하지 않는다.

`SCOPE_DENIED`는 실행 전에 차단한 조회로 기록하고 모델이 대상 내 경로로 고쳐 계속할 수 있다. 이를 실제 파일 수정·외부 접근·사람의 승인 대기로 바꾸지 않는다. 반대로 완료된 외부 native 접근이나 실행 여부가 미확정인 외부 호출은 BLOCKED로 남기며, 이후 구현 재시도나 공급자 변경으로 지울 수 없다. 모든 Kilo attempt의 `scopeAudit`은 bounded event ring 밖에 보존되고 SUCCESS에서 양성 증거와 위반 부재를 확인한다. 필드 없는 기존 그래프는 기존 정책을 유지하므로 저장된 그래프에는 이 옵션을 켜야 한다. Codex/Claude/OpenCode의 native sandbox 정책은 변경하지 않는다.

이 경계는 관찰 가능한 native 파일 도구 및 literal 조회에 대한 보호다. 임의 프로그램·MCP·plugin 내부의 모든 파일 IO를 격리하는 OS 샌드박스로 해석하지 않는다. 실제 검증에서는 native 이벤트 전체를 별도 감사해 차단된 시도와 완료된 범위 위반을 구분한다.

literal 조회는 인용된 `|`/`;`와 실제 명령 연결을 구별하며, `cat -n`, `tail -f`, `find -L` 같은 옵션 뒤 경로와 표준오류 폐기/합치기를 검사한다. 디렉터리 변경도 승인된 경계를 벗어날 수 없고 조건부 변경 뒤에는 가능한 작업 폴더 모두를 확인한다. 검증된 단순 조회·출력 준비의 대상 내부 절대 경로는 상대 경로로 바꿔 native 권한 검사에서 공백 경로를 오해하지 않도록 한다. 읽기 전용 fallback/상태 echo는 메타데이터 조회로 허용하지만 receipt를 만들지 않는다. 등록 검사의 OR/파이프/추가 인수는 기존 실제 종료코드 보존 규칙을 계속 따르며, 정확히 같은 literal argv의 인용 차이만 등록 명령으로 정규화한다.

## 필수 파일 계약과 역할별 복구

검증 계약 version 1의 선택 필드 `requiredFiles`로 제품·문서 파일과 고정 요구사항 ID를 연결한다. 예를 들어 기존 manifest에 다음 필드를 추가한다. `README.md`의 요구사항 ID는 실제 목표에서 도출한 ID를 사용한다.

```json
"requiredFiles": [
  {"path": "index.html", "requirements": ["REQ-001"]},
  {"path": "README.md", "requirements": ["REQ-001", "REQ-012"]}
]
```

목록은 1~200개, 대상 내부의 고유한 상대 파일 경로와 하나 이상의 실제 요구사항 ID를 사용한다. 출력 디렉터리·상위 경로·절대 경로는 선언할 수 없다. 누락·빈 파일·디렉터리·외부 경로·파일 심볼릭 링크는 실패다. `requiredFiles`는 수정 가능한 제품이며 `protectedFiles`는 변경할 수 없는 검사다. manifest 자체는 계속 고정하므로 실행 중 필수 파일 목록을 빼서 통과시킬 수 없다. 기존 계약의 선택 필드가 없으면 자동으로 삽입하거나 목표를 추측하지 않는다. 자체 작성 계약은 구현 프롬프트에서 제품과 문서 전체를 선언하도록 안내한다.

구현의 완료 응답을 수락하기 전에 검사하며, 누락 시 구체적인 파일·요구사항을 같은 구현 방문의 유한 완료 보완으로 전달한다. 미작성 계약은 기존 테스트 경계의 계약 준비·수정 경로를 유지한다. 테스트·검토·승인 시작 전과 완료 응답 뒤, SUCCESS 종단에서도 확인한다. 테스트 시작 전 누락은 모델 호출 없이 FAIL로, 검토·승인은 REJECTED로 구현에 반환한다. 계속 고치지 못하면 기존 단계·전체 예산 안에서 PAUSED가 된다. 파일 존재가 동작이나 문서 내용의 품질을 증명하지는 않는다.

| 역할 | 허용 동작과 실패 후 이동 |
|---|---|
| 계획 | 읽기 전용으로 목표·산출물·검사 계획을 작성한다. |
| 구현 | README를 포함한 제품, 자체 테스트, package/config를 작성·수정한다. 가장 최근 테스트·검토·승인의 실패를 별도 복구 문맥에서 먼저 읽고 해당 원인을 고친다. 고정 검사는 유지한다. |
| 테스트 | `testSourceGuard`에서는 등록 검사·읽기·verification 준비만 한다. README 누락도 직접 고치지 않고 파일·요구사항·관측 원인으로 FAIL을 반환한다. 첫 실패와 수정 시도는 구현으로 돌아간다. |
| 검토·최종 승인 | 각 `requiredFiles` 파일과 필수 자체 테스트·품질 보고서를 직접 읽은 native 증거가 필요하다. README가 요청된 실행법·규칙·조작·실제 검사 명령을 설명하는지도 판단한다. 파일 수정이나 검사 재실행은 하지 않는다. 읽기 증거/보고 형식만 부족하면 같은 역할에서 유한 보완하고, 제품 결함은 REJECTED로 구현에 반환한다. |

어떤 역할에서 제품 수정을 요청하든 구현 후 새로운 테스트 방문이 모든 등록 검사를 통과해야 한다. 과거 통과 receipt로 수정된 제품을 승인하지 않는다. 기존 테스트 프롬프트의 편집 허용 문구와 인수 오류 복구의 쓰기 안내는 소스 고정 테스트에 제공하지 않는다. 승인 거절 메타데이터도 `completionAccepted=false`로 남긴다. 그래프/연결/세션 버전, REST/SSE·공개 CLI 옵션은 유지한다.

무료 가격 표시는 현재 공급자 사용 가능성을 보장하지 않는다. Kilo의 `PROMOTION_MODEL_LIMIT_REACHED`/HTTP 429 응답은 공급자 제한 증거이며 인증 목록만으로 제한 해소나 토큰 유효성을 판정하지 않는다. 응답에 재설정 시각이 없으면 이를 추측하지 않는다. 유료 모델 전환이나 계정 변경 없이 별도의 최소 Auto Free 요청으로 사용 가능 여부를 확인한 후 새 전체 검증을 시작한다. 제한 중의 코드 회귀 성공은 실제 모델 제작·최종 승인 성공과 구분한다.

## Kilo 프로그램 내부 I/O 격리

새 자율 프리셋은 `programIoGuard=true`와 `targetScopeGuard=true`를 함께 사용한다. Kilo의 모델 도구 명령과 자식 프로세스는 호스트에서 실행하지 않고, 명령마다 별도 Apple container VM에서 실행한다. 모델 도구는 bash와 메모용 todowrite로 제한하며 native 파일 도구·task·MCP·외부 plugin·프로젝트 설정·LSP·formatter·snapshot·외부 skill 로딩을 차단한다. 기존 그래프에서 선택 필드가 없으면 종전 정책을 유지한다. REST/SSE·공개 agent-loop 옵션·저장 버전은 바꾸지 않는다.

현재 검증된 환경은 Apple Silicon macOS 26, Apple container 1.6.0이다. `container`를 설치한 뒤 `npm run sandbox:prepare`로 Node 24.21.0·현재 lockfile·Playwright/Chromium의 Linux 런타임 이미지를 준비한다. 첫 이미지 빌드는 네트워크와 8GiB 이상의 여유 공간이 필요하다. 사용자 인증·과거 CLI 세션·프로젝트 소스는 이미지에 넣지 않는다. 준비 명령은 내부 개발/설정용이며 npm 설치 단계에서 VM이나 브라우저를 자동 설치하지 않는다. 설치 패키지에서는 `node dist/src/core/program_io_setup.js`를 사용할 수 있다. 환경·lockfile·이미지 해시·버전이 맞지 않으면 실제 모델 호출 전에 BLOCKED가 되며 약한 경계로 대체하지 않는다. Windows/Linux의 강한 VM 어댑터는 아직 지원하지 않는다.

VM에는 대상 프로젝트와 읽기 전용 공개 실행기만 공유한다. 이미지 루트는 읽기 전용이고 호스트 홈·인증·소켓·다른 프로젝트·호스트 네트워크를 공유하지 않는다. `--network none`의 게스트 loopback에서 게임 서버와 Chromium 검사를 실행하므로 호스트 로컬 API에 파일 접근을 대신 요청할 수도 없다. HOME·캐시·임시 출력은 대상의 `verification/.agent-io` 아래에 둔다. 구현은 제품을 수정하고 보호된 계약 파일은 읽기 전용이다. 테스트는 verification 출력만, 검토는 호출별 임시 폴더만 수정할 수 있다. 게스트의 공개 OS/런타임 읽기는 필요하며, 이를 호스트 사용자 파일 접근과 구분한다. 공급자 CLI의 인증·네트워크 및 서명 브로커는 신뢰하는 제어 영역이다. SDK·설정 의존성은 대상 밖 세션 전용 HOME/캐시에 한 번 설치해 재사용하며 VM에는 공유하지 않는다. 호출별 서명 키·정책·scratch는 계속 분리한다. 브로커와 HOME 경계는 심볼릭 링크와 macOS 경로 별칭을 해석한 실제 경로로 확인한다. 악성 호스트 관리자나 VM/커널 자체 취약점까지 방어한다고 주장하지 않는다.

실행 전 외부 canary의 읽기·쓰기·목록·stat 및 자식 프로세스 접근을 검사한다. 실제 명령은 호출별 서명을 검증한 브로커만 실행하며, 시작/종료·실제 종료코드·이미지·네트워크·VM 삭제 기록을 대상 밖에 서명해 저장한다. native 입력을 먼저 저장하는 CLI에서도 호스트 경로 없는 서명된 after-hook 메타데이터로 실제 명령을 연결한다. 실행 뒤 원래 입력을 복원하고, 모델 대화의 사본에서도 서명을 확인해 내부 브로커 명령을 실제 제품 명령으로 되돌린다. 동일 visit의 이전 시도 공개 키로 resume 이력도 처리하며 원시 native 기록은 수정하지 않는다. 내부 브로커 명령 재호출과 빈 Bash 입력은 실행 전에 거절하고 연속 인수 오류의 유한 복구에 포함한다. 명령이 끝나면 VM을 삭제하므로 분리된 자식 서버도 남지 않는다. 등록 검사 연결과 일괄 프로세스 종료의 실행 전 거절에도 별도 표식을 붙여 미격리 실행과 구분한다. 거절은 성공 검사 receipt가 될 수 없다. 증거 누락·변조·중복·우회·미완료가 있으면 SUCCESS를 차단하고 시도도 종료된 역할 위반으로 기록한다. 원시 기록과 공개 검증 키만 보존하고 비밀 서명 키는 로그/세션에 저장하지 않는다. 게스트 PID/포트는 호스트와 별도이므로 정리 시 호스트 PID로 해석하지 않는다.
