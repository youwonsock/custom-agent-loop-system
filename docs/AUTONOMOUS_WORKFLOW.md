# 자율 제작·검증 실행

그래프 라이브러리의 **↻ 자율 제작 그래프**로 새 프리셋을 만든 뒤 CLI·모델·목표·대상 프로젝트를 지정한다. 이 프리셋은 계획 1개를 자동 선택하고, 구현 → 테스트 → 읽기 전용 검토 → 최종 승인으로 진행한다. 기존 그래프의 계획 승인 설정은 변경하지 않는다. CLI에서는 `agent-loop init --autonomous`로 같은 프리셋을 추가할 수 있다.

그래프 설정의 `자동 수정 루프`는 실패를 구현으로 되돌리며 기본 3회까지 수정한다. `실제 브라우저 검증 필수`가 켜진 웹 작업은 실제 플랫폼 검증 명령의 네이티브 종료 코드 0이 추가로 필요하다. 웹이 아닌 작업은 이 옵션을 끄고 해당 프로젝트의 실제 테스트를 사용한다. 빈 검사·보고서만 작성한 실행·생략·실패·낡은 근거로 SUCCESS를 만들지 않는다.

## 준비와 권한

- Node 24 이상과 인증된 로컬 코딩 CLI, 대상 프로젝트의 테스트 실행 환경이 필요하다.
- 웹 작업에는 `playwright`와 Chromium이 대상 프로젝트 또는 Agent Graph 설치 환경에 있어야 한다. 없으면 구현 역할이 기존 승인된 CLI 도구로 프로젝트 내부 설치를 준비할 수 있다. 설치·네트워크·권한이 거부되면 대기한다. npm 배포에 브라우저를 묶거나 자동으로 전역 설치하지 않는다.
- Codex의 `네이티브 자동 승인 검토`는 `--approve-for-me`를 지원하는 CLI에서만 사용한다. 쓰기 역할의 개별 명령을 네이티브 검토자가 승인하며 workspace-write를 사용한다. `--sandbox`와 충돌하는 인자를 함께 전달하지 않는다. 읽기 전용 역할에는 적용하지 않는다. 사용자 전역 CLI 설정은 바꾸지 않는다.
- Kilo 등 다른 CLI는 기존 네이티브 명령 승인 정책을 사용한다. 무인 실행 전에 필요한 프로젝트 명령이 해당 정책에서 허용돼 있어야 한다. 그래프는 인증·권한 거부·명시적 사람 승인을 자동 우회하지 않는다.

## 브라우저 검사 명세

구현/테스트 역할이 `.agent-graph/browser.json`을 작성한다. 검사 조건은 원래 요구사항을 충족해야 하며, 실패를 없애기 위해 명세·테스트를 약화하면 안 된다. 계획·검토·최종 승인 역할은 이 명세와 실제 테스트 기록을 읽기 전용으로 검토한다. 원래 사용자가 사람의 승인이나 운영자 전용 증거를 명시했다면 그 조건은 계속 지킨다. 자율 작업의 새 목표에는 불필요한 운영자 전용 보고서 조건을 추가하지 않는다.

```json
{
  "version": 1,
  "server": { "command": ["node", "server.mjs"] },
  "steps": [
    { "id": "desktop", "type": "viewport", "width": 1280, "height": 900 },
    { "id": "page", "type": "visible", "selector": "h1" },
    { "id": "move", "type": "click", "selector": "#move" },
    { "id": "score", "type": "text", "selector": "#score", "equals": "1" },
    { "id": "save", "type": "snapshot", "name": "score", "selector": "#score" },
    { "id": "reload", "type": "reload" },
    { "id": "persist", "type": "sameSnapshot", "name": "score", "selector": "#score" },
    { "id": "mobile", "type": "viewport", "width": 390, "height": 844 },
    { "id": "bounds", "type": "noOverflow" },
    { "id": "cells-fit", "type": "within", "selector": ".cell", "container": "#board" },
    { "id": "console", "type": "noConsoleErrors" }
  ]
}
```

지원 단계는 `viewport`, `click`, `press(key)`, `drag(selector,direction)`, `reload`, `visible`, `text(equals/contains)`, `count(equals)`, `noOverflow`, `within(selector,container)`, `snapshot(name,selector)`, `sameSnapshot`, `differentSnapshot`, `noConsoleErrors`, `http(path,status,contains)`이다. 모든 단계의 id는 고유해야 하고, 실제 assertion이 최소 하나 있어야 한다. 한 실행은 최대 100단계·120초, 파일 해시는 최대 10,000개를 허용한다. assertion은 최대 5초간 상태가 안정되는지 재확인한다. 소스 심볼릭 링크는 명시적인 프로젝트 복사본으로 풀어야 하며 제한을 넘으면 성공 대신 실패/대기로 끝난다. `http`는 경로를 미리 정규화하지 않는 실제 loopback HTTP 요청이므로 encoded traversal·잘못된 URL도 직접 검사할 수 있다. DOM mock은 브라우저 검증으로 인정하지 않는다.

서버 명령은 argv 배열이며 셸 래퍼 없이 대상 프로젝트에서 시작한다. 제공된 전용 임시 `PORT`를 사용하고 실제 `http://127.0.0.1:포트`를 출력해야 한다. 다른 포트를 출력하면 기존 서버를 재사용하지 않고 실패한다. 빌드가 필요한 프로젝트는 먼저 빌드해야 한다. 검사 중·서버 종료 중 소스가 바뀌면 다시 검사해야 한다. 브라우저 요청은 이 loopback origin으로 한정한다.

일반 수동 실행은 `agent-loop verify-browser --spec .agent-graph/browser.json`으로 가능하다. 자율 그래프는 프롬프트에 제공된 **설치된 플랫폼 CLI의 정확한 절대 경로 명령**을 실행해야 한다. 프로젝트가 만든 가짜 CLI나 `--help` 실행은 네이티브 브라우저 증거로 수락하지 않는다. 단위 검사를 먼저 실행한 뒤 브라우저 명령을 마지막에 실행한다. 디렉터리 생성·로그 읽기·보고 출력은 별도 호출로 하고, 검사 뒤에 echo·파이프·백그라운드 실행을 붙이지 않는다.

`verification/browser/<run-id>/`에 성공/실패별 report.json, 서버 로그, 최종/실패 화면, viewport 화면과 trace.zip을 보존한다. `verification/browser/report.json`은 최근 실행의 원자적 복사본이다. 보고서는 검증기가 직접 쓰며 모델이 작성하지 않는다. 새 검사를 실행해도 과거 실패 폴더를 덮어쓰지 않는다. 실행한 서버와 브라우저만 정리하며, 외부 서버는 종료하지 않는다. 실패·취소·정리 불확실·미실행 단계는 성공으로 승격하지 않는다.

## 실패·재시도

- 테스트 assertion 실패는 FAIL, 검토/승인 반려는 REJECTED로 구현에 돌아간다.
- 모델이 BLOCKED로 보고한 수정 가능한 코드/검사 준비 문제는 `BLOCKED_KIND: product` 또는 `BLOCKED_KIND: test_setup`과 실제 근거를 포함한다. 자율 그래프에서만 실패 경로로 돌린다. 기존 수동 그래프의 BLOCKED 동작은 유지한다.
- 실제 네이티브 권한 오류는 위 표식보다 우선하여 대기한다. 외부 서비스·인증·명시적인 사람 증거는 `BLOCKED_KIND: external`로 보고한다.
- 테스트 역할의 제품 파일 변경은 네이티브 변경 경로와 실행 전후 파일 해시로 감지해 반려한다. 테스트·검증 명세·로그는 별도 경로에서 작성하고, 제품 수정은 구현에서 수행한다. 빌드 산출물과 테스트 결과는 제품 수정 검사에서 제외하되 실제 브라우저 검증의 소스·자산 해시에는 빌드 산출물을 포함한다.
- 사용자 Interrupt/STOP, 수동 계획 승인, 추가 접근 승인, 무료/유료·미확인 모델의 기존 복구 한도는 유지한다. 무료도 무한 반복하지 않고 유료·가격 미확인은 공급자 한도에 도달하면 추가 호출을 멈춘다.
- 기존 블록 보고의 형식 보완은 현재 네이티브 실행 기록을 기준으로 한다. 기록이 없으면 새 검사를 실행하고, 실패 기록을 PASS로 바꾸지 않으며, 유효한 성공 기록이 있으면 파일 수정 없이 정확한 CHECK_COMMAND로 보고만 보완한다.

검증기는 실제 실행 여부와 관측된 assertion을 증명한다. 원래 목표에 충분한 검사인지, 모델이 구현을 올바르게 수정했는지는 별도의 테스트·검토·최종 승인 책임이다. 프리셋은 사람 검토를 가장하거나 공급자 가용성을 보장하지 않는다.

## 공급자·계획 형식 복구

네이티브 연결 로그와 `step_start`/`step_finish`, 빈 텍스트, 실패한 도구 이벤트는 유효한 모델 진행으로 대기 시간을 연장하지 않는다. 동일한 주 요청의 공급자 오류가 유효한 진행 없이 3회 반복되면 현재 프로세스를 종료하고 기존 유한 재시도·무료 모델 복구 정책에 넘긴다. 중복된 동일 로그는 횟수에 포함하지 않는다. 보조 제목 생성 세션의 오류는 원시 로그에 남기되 주 요청의 진단·재시도 원인으로 사용하지 않는다. 실제 401/403 인증·권한 중단 정책은 유지한다.

동일한 도구 스키마/사용 불가능 오류가 서로 다른 호출에서 3회 연속 관측되면 `tool_arguments`로 중단한다. 정상 도구 완료나 다른 오류는 이 연속 횟수를 초기화한다. 읽기 전용 역할의 권한을 확대하지 않으며, 새 시도에는 역할별 `read`/`glob`/`grep` 또는 쓰기 역할의 `bash`/`write` 스키마 안내를 전달한다.

계획 선택지마다 모든 고정 요구사항을 참조해야 하며 프롬프트는 전체 ID 표기를 권장한다. 계획의 명확한 `REQ-006/007`, `REQ-006,007`, `REQ-001..024` 목록·범위는 알려진 ID 집합으로 해석하되 원래 계획 본문을 고치지 않는다. 알려지지 않은 끝점·역방향 범위·실제 누락은 선택지별로 알리고 보고를 보완한다. 이 정규화는 계획 참조에만 적용하며 테스트·QA·최종 승인의 각 고정 ID 증거 블록과 실제 실행 게이트에는 적용하지 않는다.

일부 네이티브 검사만 성공한 경우에는 전체 검증이 완료된 것으로 간주하지 않는다. 이전 보고의 CHECK_COMMAND와 수락된 성공 기록을 대조해 빠진 실제 검사만 단독 명령으로 실행하도록 보완한다. 모든 보고된 검사 기록이 이미 있을 때만 형식 보완으로 처리한다. 계획·QA·최종 승인 역할에는 브라우저 명령을 계획/감사 대상으로만 제공하며 실행이나 명세 작성을 지시하지 않는다. 검증기가 설치 위치의 Playwright를 사용할 수 있으므로 대상 프로젝트의 require 실패만으로 환경 제약을 선언하지 않는다.

## 고정 검증 계약과 구조화 보고

새 자율 프리셋은 `automation.verificationContract=true`를 사용한다. 기존 그래프 version 2·연결 version 1·세션 stateVersion 3과 localStorage 키는 유지한다. 이 옵션이 없는 기존 그래프는 종전 보고 계약을 사용한다.

대상 프로젝트의 `.agent-graph/verification.json`은 필수 검사와 요구사항 연결을 선언한다. 시작 전에 제공된 계약은 첫 모델 호출 전에 보호 파일과 함께 SHA-256으로 고정하며 출처는 `supplied`로 기록한다. 없으면 구현 역할이 인수 테스트와 계약을 만들고 첫 테스트 진입 때 고정한다(`implementation`). 계약 누락·오류는 테스트 준비 실패로 구현에 돌아가며 유한 수정 한도 안에서 처리한다. 시작 전에 잘못된 계약이 있으면 호출 없이 요청을 거부한다.

```json
{
  "version": 1,
  "protectedFiles": ["tests/verify-acceptance.mjs", ".agent-graph/browser.json"],
  "checks": [
    { "id": "acceptance", "command": "node tests/verify-acceptance.mjs", "requirements": ["REQ-001"] },
    { "id": "browser", "command": "<프롬프트가 제공하는 설치된 플랫폼의 정확한 명령>", "requirements": ["REQ-001"] }
  ]
}
```

모든 고정 REQ ID가 검사에 연결돼야 하며 **등록된 모든 검사**가 테스트 역할에서 실제 성공해야 한다. 한 검사가 모든 ID에 연결돼 있어도 다른 검사를 생략할 수 없다. 웹 계약은 플랫폼 브라우저 명령과 보호된 browser.json을 포함한다. npm script 이름만 등록하는 대신 보호된 인수 검사 실행 파일을 직접 실행하는 검사도 필요하다. 보호 파일은 최대 200개·개별 10MiB·전체 50MiB이며 심볼릭 링크와 프로젝트 밖 경로는 거부한다. 계약 자체도 보호한다. 매 시도 전후와 성공 종단에서 해시를 확인하며, 보호 파일 변경·삭제·읽기 실패 또는 네이티브 이벤트의 쓰기 관측(원상복구 포함)은 BLOCKED가 된다. 이 검사는 적대적인 운영체제나 악성 CLI를 격리하는 보안 샌드박스는 아니다.

고정 계약의 테스트·검토·최종 승인 역할은 아래 형식으로 판단만 보고한다. CHECK_COMMAND나 PHASE_DONE을 모델이 복사할 필요가 없다.

```text
[AGENT_REPORT]
{"version":1,"verdict":"PASS","requirements":[{"id":"REQ-001","status":"SATISFIED","evidence":"관측한 assertion과 결과"}]}
[/AGENT_REPORT]
```

테스트 verdict는 PASS/FAIL/BLOCKED, 검토·승인은 APPROVED/REJECTED/BLOCKED이다. 요구사항 status는 SATISFIED/PARTIAL/FAILED/BLOCKED이며, PASS/APPROVED에는 모든 고정 ID가 필요하다. 오류 보고에는 실패한 항목만 넣어도 된다. BLOCKED에는 `blockedKind: product|test_setup|external`을 사용할 수 있다. 엔진이 고정 검사 ID와 실제 네이티브 명령·종료코드·receipt ID를 연결해 기존 화면용 증거로 변환한다. 형식 오류·중복·알 수 없는 ID를 거부하고, 실제 검사 실패·미실행·권한 오류를 성공으로 바꾸지 않는다. 검토와 최종 승인은 현재 테스트 증거를 읽기 전용으로 감사한다.

검사 연결과 고정 해시는 검사의 실행·보존을 증명한다. 검사 내용이 도메인의 모든 요구사항을 충분히 검증하는지는 인수 테스트 작성자와 독립 검토의 책임이다. 모델이 직접 만든 검사의 출처를 외부에서 제공된 인수 기준과 동일하게 표현하지 않는다.

## 전체 실행 예산

새 실행에는 단계 복구 예산과 별개로 `sessionTimeoutMs`(기본 60분), `maxSessionAttempts`(기본 24회)를 저장한다. 화면의 전체 시간·전체 에이전트 시도 한도에서도 설정한다. 시간은 시작부터 대기·백오프·재개·재시작 시간을 포함한 wall-clock이다. 시도 수는 네이티브 에이전트 CLI 호출 수이며 보고 보완·무료 복구도 포함한다. **CLI 내부의 공급자 요청 수·토큰·금액을 제한하는 과금 예산은 아니다.**

한도가 소진되면 PAUSED로 정지하고 자동 복구 예약을 취소한다. 실행 중에는 전체 마감 시각으로 자식 CLI를 종료한다. 예산 소진 상태는 수동 재개·무료 복구·워커 재시작으로 초기화하지 않는다. 마지막 허용 시도가 마감 전에 성공하면 결과를 수락할 수 있다. 기존 저장 세션에 전체 예산이 없으면 종전 정책으로 읽으며 데이터를 자동 변경하지 않는다. 기존에 완료한 SUCCESS 기록은 이후 시간이 지났다는 이유로 무효화하지 않는다.

새 자율 프리셋은 단계 10분·도구 5분·단계 복구 31분·네이티브 기본 시도 3회·무료 추가 복구 1회(15초 대기)를 사용한다. 명시적인 설정값은 우선한다. 공급자 장애·인증·권한·불명확한 워커 소유권은 계속 성공을 차단하며, 예산은 이런 외부 조건의 가용성을 보장하지 않는다.
